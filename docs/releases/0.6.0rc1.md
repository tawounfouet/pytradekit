# PyTradeKit 0.6.0rc1 - Reconciliation & Recovery

**Status:** Release candidate after deterministic code and PostgreSQL qualification.

## Scope

PyTradeKit 0.6.0rc1 turns reconciliation and recovery into a first-class capability layered on the durable 0.5 Alpaca PAPER runtime.

~~~text
LOT-01  Reconciliation Domain Foundations
LOT-02  Snapshots & Comparators
LOT-03  Persistence
LOT-04  Application Reconciliation
LOT-05  Missing Facts & External Activity
LOT-06  Recovery Workflows
LOT-07  Consistency / Confidence Integration
~~~

The release candidate implements the planned version progression from 0.6.0a1 through 0.6.0rc1 on main.

## Reconciliation model

The generic pipeline is explicit:

~~~text
trigger
-> create ReconciliationRun
-> capture InternalSnapshot
-> capture BrokerSnapshot
-> compare canonical facts
-> persist Mismatch evidence
-> plan explicit Resolution records
-> apply only supported recovery actions
-> capture fresh verification evidence
-> compute ConsistencyStatus + StateConfidence
-> publish safety evidence
~~~

A completed run does not imply consistency.

Provider SDK models do not enter the reconciliation domain.

## Durable evidence

PostgreSQL now contains a dedicated reconciliation schema:

~~~text
reconciliation.runs
reconciliation.mismatches
reconciliation.resolutions
~~~

Evidence is checkpointed during recovery so a crash does not erase already-observed mismatches or lifecycle progress.

Active-run ownership and optimistic concurrency prevent overlapping reconciliation from silently overwriting evidence.

## Missing Fill Recovery

Alpaca FILL account activities provide stable external execution identities.

The automatic path is intentionally narrow:

~~~text
proven provider FILL
-> stable external_fill_id
-> canonical order mapping
-> canonical Fill
-> ProcessFill
-> OMS
-> Portfolio
-> ProcessedFillRegistry
-> ExternalFillImported Outbox
~~~

The same external fill is idempotent across replay.

Cumulative order fields such as filled quantity never fabricate canonical Fill records.

## External activity

Provider activity without proven internal origin remains explicit.

~~~text
INTERNAL
EXTERNAL_MANUAL
EXTERNAL_SYSTEM
BROKER_ADJUSTMENT
UNKNOWN_EXTERNAL
IMPORTED
~~~

Unknown external orders are not silently turned into strategy orders.

## Recovery workflows

The same reconciliation engine is used for:

~~~text
STARTUP
PERIODIC
RECONNECT
SUBMIT_UNCERTAINTY
INCIDENT
MANUAL
~~~

Stale active runs can be closed before a fresh recovery attempt.

## Consistency and confidence safety

Trading admission is fail-closed when reconciliation evidence is unsafe.

~~~text
CONSISTENT + HIGH
        |
        +-> TradingReadiness may be READY
        +-> SubmitOrder may create new risk
        +-> StrategyRuntime may emit new targets

anything else
        |
        +-> new risk blocked
        +-> strategy targets suppressed
~~~

An economic correction is also rejected if the internal watermark changed after the original comparison.

An applied resolution is verified only by evidence strictly newer than the recovery effect.

## Alpaca PAPER startup integration

The existing 0.5 startup remains the provider-specific baseline, but it is no longer the final authority for trading readiness.

~~~text
0.5 startup prerequisites
-> durable/provider convergence
-> authenticated trade_updates
-> second 0.5 reconciliation
-> generic 0.6 ReconcileAccount
-> CONSISTENT + HIGH
-> TRADING_READY
~~~

The 0.6 gate fails closed on generic reconciliation errors.
